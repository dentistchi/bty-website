## Instructions
1. **Run the entire SQL file without edits** in the Supabase SQL Editor (read-only: only
   `pg_catalog` / `information_schema` / `aclexplode`; no application rows; privileges compared as
   exact ACL tuples, not effective access).
2. **Export exactly one result** — the single `audit` cell (JSON, a `{ "audit": … }` wrapper, or the
   single-cell CSV all work).
3. **Do not edit the JSON/CSV.**
4. **Run the comparator.** It recomputes the packet identity from the checked-in files, verifies it
   matches the manifest, then verifies the export's embedded packet metadata before comparing.
5. **Stop on `PACKET REJECTED`** — no trusted comparison occurred (stale/edited export, changed file,
   or wrong version). Re-run the CURRENT generated SQL and re-export.
6. **Return the machine report** (per-migration A/D/E, grouped by final authority; `submit_followup`
   is judged under `20260729`).
7. **This authorizes no repair or schema change.** An `A` candidate is not permission to
   `supabase migration repair`, `db push`, or apply any migration (single live DB = production).

Do not copy individual catalog sections; the whole packet is machine-compared.

---
The audited migrations create no policies (RLS-on, deny-all → `policies: []`) and grant EXECUTE only
to `service_role` (all other roles revoked → exact ACL `[{service_role, EXECUTE, non-grantable}]`;
tables have no controlled-role ACL tuples). Any deviation surfaces as a `CONFLICT`, not a manual item.
